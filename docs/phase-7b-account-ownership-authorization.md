# Account Ownership Authorization Implementation Phase (Phase 7b)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this phase task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bind every account to the JWT subject that created it, and enforce that binding where it actually can be enforced. A customer can debit, and read the full detail of, only an account they own — closing Phase 7's documented gap where any authenticated `customer` could debit any account by calling Account Service directly. The mirror-image gap on `credit` cannot be closed the same way and stays deliberately deferred — see Design Decisions. Both services' unscoped "list everything" endpoints (`GET /accounts`, `GET /transfers`) move behind new admin roles, held by a new demo admin user rather than any customer, since neither has a real end-user story once ownership exists; the single-item reads a customer actually uses (`GET /accounts/{id}`, `GET /transfers/{id}`) get scoped to what they own instead. Fraud and Notification are untouched — neither has an ownership concept.

**Architecture:** `Account` gains an `ownerId` column (a `UUID`, set from the caller's JWT `sub` at creation, never client-supplied) alongside the existing free-text `ownerName`. `Transfer` gains an `initiatorId` column (same idea — the JWT `sub` of whoever called `POST /transfers`, captured for free since Transfer already sees that token). Two new realm roles, `account-admin` and `transfer-admin`, gate the two list-all endpoints, granted to a new demo admin user (not `customer`) so the admin path has a real, demoable 200 case, not just 401/403 tests. A new internal-only endpoint, `GET /accounts/exists/{id}`, gives Transfer's pre-validate step a way to confirm an account exists without needing to own it or read its balance — replacing the relayed full-detail call that would otherwise break for every transfer to a different customer's account.

**Tech Stack:** No new dependencies. Reuses Phase 7's Spring Security OAuth2 Resource Server wiring, `KeycloakRealmRoleConverter`, and realm-export mechanism — this phase only adds two role entries to the existing `showcase-realm.json` and two entity columns via `ddl-auto: update` (no Flyway/Liquibase in this project).

**Spec:** This document (brainstormed with the user on 2026-09-17) and `docs/phase-7-auth-keycloak-jwt.md`'s Scope Boundary (which deliberately deferred this here) and Known Gaps (the direct-debit and direct-credit findings this phase resolves and re-documents, respectively).

## Design Decisions Worth Knowing Before You Start

**Why `debit` gets an ownership check but `credit` doesn't — and why the `credit` gap stays open.** Phase 7's token-relay design (`AuthorizationPropagatingInterceptor`) relays the *initiating customer's own* JWT for every outbound call Transfer makes on their behalf, both legs of a transfer alike. That means the debit call on the source account and the credit call on the destination account arrive at Account Service carrying the identical token — the source customer's. Enforcing "caller must own this account" on `debit` is exactly what closes Phase 7's documented gap (a customer directly debiting an account they don't own). Enforcing the same rule on `credit` would break every real transfer to a different person, since the destination is never owned by the token making the call. So `credit` keeps no ownership check, and the gap Phase 7 already flagged — an authenticated customer can call `POST /accounts/{id}/credit` directly and mint money into any account, bypassing the saga and its ledger entirely — is unaffected by this phase and stays documented, not fixed. Closing it would need Transfer to stop relaying the customer's token for `credit` and use its own machine identity instead, which is a real redesign of Phase 7's core relay decision, not an ownership check — out of scope here (see Scope Boundary). **Update, post-Phase 9:** closed. `credit` now requires its own `account-crediter` authority, held only by `transfer-service`'s machine identity and not by the `customer` composite, and Transfer sends every credit call (live leg and compensation credit-back alike) with that identity rather than the relayed customer token (`AuthorizationPropagatingInterceptor.USE_SERVICE_IDENTITY`). `debit` and the fraud checks still relay the customer's token. A customer calling `credit` directly now gets 403.

**Why an ownership denial reuses `AccountNotFoundException` (404, `ACCOUNT_NOT_FOUND`) instead of a new 403.** Phase 7's highest-severity finding fixed `AccountClient.rejected()` to treat *every* 401/403 as `AccountServiceUnavailableException` — ambiguous, retryable — specifically because a generic Spring-Security 403 (denied before Account's own body is ever produced) looks identical to one carrying a real RFC 7807 problem body, and conflating them let a credential hiccup get misread as a definitive business rejection. An ownership-denial response would collide with exactly that carve-out if it also used 403: it's a clean, definitive rejection (like insufficient funds), not an ambiguous one, but it would be swallowed into "maybe retry" regardless. Returning 404/`ACCOUNT_NOT_FOUND` instead — "as far as you're concerned, this account doesn't exist" — sidesteps the collision entirely: it already flows through the normal problem-body path into `AccountRejectedException`, and `TransferFailureCode.fromAccountCode()` already maps it. No changes needed to the carefully-fixed `AccountClient` classification logic. It also happens to be the standard don't-confirm-existence-to-non-owners pattern, which is a bonus, not the primary reason.

**Why `GET /accounts/exists/{id}` is a new endpoint rather than reusing `HEAD /accounts/{id}`.** Phase 7's review already added a `HEAD /accounts/{id}` matcher (gated on `account-reader`, no ownership) specifically so a HEAD couldn't leak existence via a role check gap. But Spring MVC serves `HEAD` from the same `GET` handler method as `GET /accounts/{id}` — so once that method's *service-layer* logic gains an ownership check, `HEAD /accounts/{id}` inherits it too, since it is the same code path. `HEAD` therefore stops being a general existence probe the moment ownership lands on `GET`, whether anyone means it to or not. A dedicated endpoint, on its own controller method and its own service call with no ownership check in it, avoids that silent coupling.

**Why `GET /transfers/{id}`'s destination-owner branch calls Account live instead of denormalizing the destination's owner onto `Transfer`.** `initiatorId` is free — Transfer already holds the caller's own JWT when `POST /transfers` runs, no extra call needed. The destination's owner is not free: Transfer would have to ask Account for it, and the whole point of the `exists`-endpoint split is that finding out who owns an account is exactly the thing a non-owner should not be able to do (mirrors real banking — sending money to an account needs only its number, not its owner's identity). Storing the destination's owner on every `Transfer` row would mean Account leaking exactly that information to Transfer at creation time for every transfer ever made, just to serve a read path that isn't hit for most transfers. A live per-read check (Transfer asks Account's owner-gated `GET /accounts/{id}` using the *reader's own* relayed token — 200 means they own it, 404 means they don't) only touches Account when someone who isn't the initiator is actually trying to look at a specific transfer, and never stores owner information Transfer has no other use for.

*Later reuse (post-Phase 12):* `GET /transfers/mine`'s incoming half follows the same principle — rather than store destination owners, Transfer asks Account's owner-scoped `GET /accounts/mine` with the reader's relayed token for the caller's account IDs on each read (`AccountClient.callerAccountIds`), then lists `COMPLETED` transfers into those accounts.

**Why `debit`'s ownership check exempts Transfer Service's own machine identity.** `CompensationScheduler.sweepStalePending()`'s `reconcileDebit()` calls `accountClient.debit()` from the `@Scheduled` thread — no inbound request, so `AuthorizationPropagatingInterceptor` has no `SecurityContextHolder` entry to relay and falls back to `transfer-service`'s client-credentials token. That token's `sub` is the service account's own id, never a customer's `ownerId`. An unconditional ownership check would make every stale-`PENDING` recovery 404 as "not yours," breaking the reconciliation machinery `CLAUDE.md` explicitly calls out as hard-won (see its "Before starting Phase 3" note). The check therefore allows the caller through when `caller.sub == account.ownerId` **or** the caller is the trusted `transfer-service` machine identity, recognized by the JWT's `azp` claim (Keycloak's standard "authorized party" claim for a client-credentials token) equaling `transfer-service`. This is not a broad bypass: it only ever fires on `debit`, replaying an operation against an account Transfer's own persisted saga state already targeted once — it never lets the machine identity act on a caller-supplied account it has no prior record of. The live saga's own `debit` call is unaffected either way — it always runs on the request thread with the real customer's token relayed, so it satisfies the ownership check normally, without needing the exemption. Worth naming plainly: this raises the stakes of the `transfer-service` client secret (`docker/keycloak/showcase-realm.json`) — before this phase it bought `account-editor`/`fraud-checker`, the same authorities any `customer` token already had; after it, it uniquely grants unconditional debit of every account. No change to how that secret is stored or rotated is in scope here, but a future hardening pass on secret handling should treat this client as higher-value than it was.

**Why `account-admin`/`transfer-admin` are new roles, granted to a new demo admin user, rather than reusing an existing one.** No admin persona exists anywhere in this project yet. Two narrow, single-purpose roles follow the same pattern as the other four capability roles: precise, not speculative. Unlike Phase 7's roles (which stayed unassigned because nothing in that phase's scope called them), this phase's own list-all endpoints need a real 200 case to demo and to test against, not just 401/403 — so a new demo user (`admin`, distinct from the `ada`/`bob` customer-named pair by design) is seeded holding both `account-admin` and `transfer-admin` directly, not via a composite, and not holding `customer` — an admin login is a distinct persona from a customer one, not a superset of it, and nothing in this phase needs it to be both.

**Why `ownerId`/`initiatorId` are set server-side from the JWT `sub`, never from the request body.** `CreateAccountRequest`'s wire shape is unchanged (`ownerName` + `initialBalance` only) — accepting an owner id from the client would let any caller create an account "owned" by someone else. This is the first place either service needs a claim value rather than just a role, so both `AccountController`/`AccountService` and `TransferService` gain a small, new (for this codebase) pattern: pull the subject off `@AuthenticationPrincipal Jwt jwt` (`jwt.getSubject()`), the standard Spring Security OAuth2 Resource Server idiom, rather than reading `Authentication`/`SecurityContextHolder` directly as `AuthorizationPropagatingInterceptor` does today (that class needs the whole token to relay; a controller only needs the one claim).

## Data Model

- `Account.ownerId` — `UUID`, `nullable = false`, set once at construction from the creating caller's JWT `sub`. `ownerName` is untouched: still free-text, still just a display label, still client-supplied.
- `Transfer.initiatorId` — `UUID`, `nullable = false`, set once at construction from `POST /transfers`'s caller's JWT `sub`.
- No Flyway/Liquibase in this project — `ddl-auto: update` on both services picks up the new columns automatically. There is no backfill for pre-existing rows; local dev's Postgres volumes have no data worth preserving across this change, but a `docker compose down -v` once (per service, if either volume already exists locally) avoids Hibernate choking on a `NOT NULL` column with no default over existing rows.

Two new realm roles, added to `docker/keycloak/showcase-realm.json`, same "permission" kind as the existing four:

| Role | Kind | Granted to |
|---|---|---|
| `account-admin` | permission | `admin` (direct grant) |
| `transfer-admin` | permission | `admin` (direct grant) |

`customer`'s composite membership is unchanged — still exactly the original four permissions (`transfer-executor`, `account-reader`, `account-editor`, `fraud-checker`). Demo users `ada`/`bob` stay `customer`-only, as today. ## Per-Endpoint Authorization Matrix (Changes from Phase 7)

Unlisted endpoints are unchanged from Phase 7's matrix. "Ownership" below means a service-layer check (caller's JWT `sub` vs. the row's owner/initiator column), separate from and in addition to the role check, which stays a static `SecurityConfig` matcher as before.

| Service | Endpoint | Required permission | Ownership check |
|---|---|---|---|
| Account | `GET /accounts` (list) | `account-admin` **(changed from `account-reader`)** | none |
| Account | `GET /accounts/{id}`, `HEAD /accounts/{id}` | `account-reader` (unchanged) | **new** — caller must own the account, else 404 |
| Account | `GET /accounts/exists/{id}` **(new endpoint)** | `account-reader` | none — existence only, no body |
| Account | `POST /accounts/{id}/debit` | `account-editor` (unchanged) | **new** — caller must own the account, else 404. Exempts the `transfer-service` machine identity (`azp` == `transfer-service`), which may debit any account — needed for `CompensationScheduler`'s reconciliation replay, see Design Decisions. |
| Account | `POST /accounts/{id}/credit` | `account-editor` (unchanged) | none — cannot be enforced, see Design Decisions |
| Account | `POST /accounts` | `account-editor` (unchanged) | n/a — `ownerId` bound to caller, not checked against anything |
| Transfer | `GET /transfers` (list) | `transfer-admin` **(changed from `transfer-executor`)** | none |
| Transfer | `GET /transfers/{id}` | `transfer-executor` (unchanged) | **new** — caller must be the initiator, or must own the destination account (live check against Account), else 404 |
| Transfer | `POST /transfers` | `transfer-executor` (unchanged) | n/a — enforced downstream, by `debit`'s own ownership check on the source account |
| Gateway | *(no route added for `GET /accounts/exists/{id}`)* | — | This is an internal Transfer→Account call only, same "no route = unreachable externally" pattern Phase 6 used for `debit`/`credit`. Existing routes for `GET /accounts`, `GET /accounts/{id}`, `GET /transfers/**` are otherwise unchanged — the role/ownership narrowing happens at the resource server, same as every other Gateway-fronted check. |

## Account Service Changes

- `AccountController`/`AccountService`: `createAccount` takes the caller's `sub` (via `@AuthenticationPrincipal Jwt`) and passes it through to `new Account(ownerId, ownerName, initialBalance)`; `CreateAccountRequest`'s fields are unchanged.
- `debit` and `getAccount` (the `GET /accounts/{id}` handler) both take the caller's `sub` and compare it against the loaded account's `ownerId` before doing anything else; a mismatch throws `AccountNotFoundException` (reusing the existing exception and its existing `ApiExceptionHandler` mapping — no new exception class, no new problem code). `debit`'s check additionally passes if the caller's JWT `azp` claim is `transfer-service` (the machine-identity exemption — see Design Decisions); `getAccount`'s does not need this exemption, since nothing calls the owner-gated `GET /accounts/{id}` with the machine token — Transfer's own reads go through `GET /accounts/exists/{id}` instead.
- New `GET /accounts/exists/{id}` controller method + a corresponding `AccountService` method that loads the account (still throwing `AccountNotFoundException` if it's genuinely missing) and returns nothing but the status — no `AccountResponse` body, no ownership check.
- `AccountResponse` gains an `ownerId` field — harmless to expose now that `GET /accounts/{id}` is owner-gated; only the owner ever sees their own response.
- `SecurityConfig`: `GET /accounts` moves from `account-reader` to `account-admin`; new matcher for `GET /accounts/exists/{id}` on `account-reader`. `GET`/`HEAD /accounts/{id}` and `POST /accounts/{id}/debit` keep their existing role matchers — the ownership check is not expressible as a static `SecurityConfig` rule (it depends on the loaded row) and lives in the service layer instead.

## Transfer Service Changes

- `Transfer` entity: new `initiatorId`, set in its constructor alongside `fromAccountId`/`toAccountId`/`amount`.
- `TransferService.execute`: takes the caller's `sub` (from `@AuthenticationPrincipal Jwt` on `TransferController.createTransfer`) and passes it straight into the `Transfer` constructor — no Account call needed for this part.
- `AccountClient.getAccount()`: pre-validate step switches from `GET /accounts/{id}` to `GET /accounts/exists/{id}` for both legs. `AuthorizationPropagatingInterceptor` is unchanged — this call still relays the caller's own token exactly as before, it just hits an endpoint that doesn't care who's asking. (An earlier version of this design considered switching pre-validate reads to Transfer's machine token instead of splitting the endpoint; the endpoint split is simpler and is what's specified here — don't reintroduce the machine-token-for-reads idea.)
- `TransferService.getTransfer`: if the caller's `sub` equals the `Transfer`'s `initiatorId`, return it. Otherwise, call a new `AccountClient` method that hits Account's owner-gated `GET /accounts/{id}` for `toAccountId`, using the *reader's own* relayed token (the existing interceptor already does this by default — no change needed there either): a 200 means the reader owns the destination, so return the transfer; a 404 (via `AccountRejectedException`/`ACCOUNT_NOT_FOUND`) means they don't, so `getTransfer` throws `TransferNotFoundException` (reused, same info-hiding convention as Account's own 404 reuse).
- `TransferController`/`SecurityConfig`: `GET /transfers` (exact path, the list) moves to `transfer-admin`; `GET /transfers/{id}` keeps `transfer-executor`, with the ownership branch added in `TransferService.getTransfer` as above.

## Testing

- **Account ownership matrix** (extends `AccountSecurityIT`'s existing pattern): `debit`/`GET /accounts/{id}` as the owning `sub` → 200; as a different `sub` → 404 `ACCOUNT_NOT_FOUND`. `GET /accounts/exists/{id}` → 200/404 regardless of which `sub` is asking, as long as it holds `account-reader`. `GET /accounts` → 403 without `account-admin`, 200 with it (a stub JWT carrying `account-admin` — mirroring the `admin` user, not literally its token).
- **Transfer ownership matrix** (extends `TransferSecurityIT`'s existing pattern): `GET /transfers/{id}` as the initiator → 200; as a mocked-owning different `sub` (Account client stubbed to return 200 for the ownership check) → 200; as an unrelated `sub` (Account client stubbed to return 404) → 404. `GET /transfers` → 403 without `transfer-admin`, 200 with it.
- **Existing tests need a consistent `sub`.** Every existing test that creates an account and then acts on it (`AccountServiceTest`, `AccountSecurityIT`'s 200-path cases, `TransferServiceTest`, `CompensationSchedulerTest`, etc.) now needs its stub JWT's `sub` to match the account's `ownerId` — `spring-security-test`'s `jwt()` post-processor sets this via `.jwt(builder -> builder.subject(...))`. Audit every green 200-path test that touches `debit`/`getAccount`/`getTransfer` for this, not just the new ownership-specific ones — a mismatched `sub` in an existing fixture will now 404 where it used to pass, and that failure mode looks like "the endpoint doesn't exist" rather than "ownership check failed," so read the actual assertion failure carefully rather than assuming a flake.
- **`AccountSecurityIT`/`AccountServiceTest` needs a machine-identity exemption case for `debit`.** A stub JWT with `azp` = `transfer-service` and a `sub` that does *not* match the target account's `ownerId` must still succeed — this is the case that protects `CompensationScheduler.reconcileDebit()` (see Design Decisions); without a test for it, a future "tighten the ownership check" edit could silently remove the exemption and break stale-`PENDING` recovery with no red test to catch it. Pair it with a negative case: a `customer`-role token (no `transfer-service` `azp`) with a mismatched `sub` still gets 404, to prove the exemption isn't just "any unmatched `sub` passes."
- **`CompensationScheduler`'s own tests need no changes.** They mock `AccountClient` entirely (per the class javadoc's existing caveat about the AOP proxy), so they never exercise the real HTTP call or its authorization — the exemption above is proven at the Account-service boundary, not here. `credit`'s calls (`compensateSource`, `reconcileCredit`) are unaffected either way, since `credit` never gained an ownership check.

## Scope Boundary

**In scope:** `ownerId`/`initiatorId` columns; binding both to the caller's JWT `sub` at creation; ownership enforcement on `debit` and on the single-item reads (`GET /accounts/{id}`, `GET /transfers/{id}`); the new `GET /accounts/exists/{id}` endpoint; `account-admin`/`transfer-admin` roles gating the two list endpoints; roadmap updates.

**Explicitly out of scope** — named follow-ups, not oversights:

| Deferred | Why not now | Lands in |
|---|---|---|
| Direct-`credit` money-minting (a customer can still call `POST /accounts/{id}/credit` on any account directly, bypassing the saga) | Cannot be fixed with an ownership check — the relayed token on a real transfer's credit leg is never the destination owner's. Fixing it needs Transfer to stop relaying the customer's token for `credit` specifically and use its own machine identity instead, which is a real change to Phase 7's core relay design, not an ownership check. Flagged and deliberately left open during this brainstorm, same as Phase 7 first flagged it. | **Resolved post-Phase 9:** `credit` requires `account-crediter`, held only by `transfer-service`, which sends credit calls as itself |
| Self-service "list my accounts" / "list my transfers" | Neither list-all endpoint had a real end-user story before this phase either (Transfer's pre-validate never used the list endpoint; nothing served a customer's own transfer history from it). Admin-gating them is a strict improvement over "anyone can list everything," not a regression against a feature that existed. A scoped "mine" listing is a real, separable feature for whenever a UI phase needs one. | Not yet scheduled |
| Keycloak fine-grained "Authorization Services" (resource/scope/policy engine) | Re-affirmed from Phase 7: realm roles + composites plus this phase's app-level `sub`-vs-`ownerId` comparison already express everything needed. | Not currently planned |
| Multi-account-per-owner tooling (e.g. enumerating every account a `sub` owns) | Nothing in this phase needs it — `debit`/`GET /accounts/{id}` check one account's `ownerId` against one caller, `POST /transfers` never needs to know how many accounts a caller has. Structurally still possible (no uniqueness constraint on `ownerId`), just nothing consumes it yet. | Revisit if a "my accounts" listing (above) gets scheduled |
